# Схемы сообщений в топиках брокера сообщений Kafka

В этом каталоге содержится спецификация топиков (очередей, журналов) и структур сообщений в этих топиках.

## Структура каталога

1. Нормативная структура каталога `backend/messaging/<группа топиков>/<имя топика>/<тип сообщения>.yaml`.
   1. В простых случаях имя топика и имя группы могут совпадать.
   2. В сложных случаях у топика может быть иерархия групп.
2. Внутри папки-топика лежат yaml-файлы, каждый из которых содержит описание в формате OpenApi структуры сообщения ОДНОГО типа, имя файла соответствует типу сообщения.
3. Файлы *.yaml на верхнем уровне каталога `messaging` содержат общие компоненты, на которые ссылаются описания в конкретных типах сообщений.

## Требования к содержанию yaml-файлов

1. Параметр `info.title` содержит в kebab-case имя типа сообщения
   1. Только латинские буквы, цифры, подчеркивание и минус;
   2. Начинается всегда только с буквы;
   3. Значение совпадает с единственным значением проперти `#/components/schemas/MessageHeaders/properties/schemaName`.
2. В `components/schemas` всегда определены минимум три компонента:
   1. `Message` - ссылкается на `MessageHeaders` и `MessagePayload`;
   2. `MessageHeaders` - описывает заголовки сообщения;
   3. `MessagePayload` - описывает тело сообщения.

## Сообщения

Каждое сообщение в Kafka содержит три компонента:

1. Ключ (`key`) - специальный заголовок, на основании которого брокер маршрутизирует сообщения между партициями:
   1. Брокер и гарантирует, что сообщения с одним и тем же ключом будут отданы консьюмерам в том же порядке, в котором они были опубликованы (по FIFO).
   2. Все сообщения в обязательном порядке должны содержать этот ключ без исключений.
2. Заголовки (`headers`) - коллекция ключ-значения, где ключ - строка, а значение всегда скалярные (не объекты).
   1. Коллекция заголовков сообщения описывается атрибутом `#/components/schemas/Message/properties/headers` в yaml-файле структуры сообщения:
      1. Имя каждой property - это имя имя заголовка;
      2. Тип property описывает тип и дефолтные значения заголовка;
      3. Тип значения заголовка всегда скалярный (не объект).
   2. Заголовки содержат простые метаданные сообщения, на основании которых консьюмер может принять решение, надо ли вообще обрабатывать это сообщение и как это делать, до десериализации, содержащего сложную структуру, тела сообщения.
   3. У всех без исключения сообщений всегда задается минимальный набор заголовков:
      1. `key` - см п.1 выше;
      2. `schemaName` - тип сообщения, строка, совпадающая с именем файла openapi;
      3. `createdAt` - момент времени, когда сообщение было опубликовано в топике;
      4. `schemaVersion` - номер версии структуры в формате semver.
   4. Все заголовки передаются только и исключительно в коллекции `headers` сообщения, дублирование заголовков в теле сообщения недопустимо.
3. Тело (`payload`) - JSON произвольной структуры
   1. Структура тела сообщения описывается компонентом `#/components/schemas/Message/properties/payload`;
   2. Тело сообщения содержит то и только то, что описано в `#/components/schemas/Message/properties/payload` и дублирование в теле коллекции заголовков бессмысленно и недопустимо.
4. При реализации тело сообщения содержит только и исключительно поля, определяемые атрибутом ``#/components/schemas/Message/properties/payload`, заголовки сообщения в тело сообщения не дублируются.

## Kafka consumer в сервисе

Из messaging-артефакта (`openapi-codegen` 1.6.0+, ADR-26061101) генерируются `*Consumer`, `*Bindings`, `TopicListener` и auto-configuration.

1. Реализуйте `{Schema}V{Major}Consumer` как Spring bean.
2. Добавьте `{Schema}V{Major}Bindings.FUNCTION_NAME` в `spring.cloud.function.definition`.
3. Настройте binding `{Schema}V{Major}Bindings.BINDING_IN` на топик `{Schema}V{Major}Bindings.TOPIC`.
4. Для binding укажите `value.deserializer: org.apache.kafka.common.serialization.ByteArrayDeserializer`.

Имя топика: `{первая_группа_каталога}.{info.title}` (например `currency-valuables.currencies-classifier-element-archived`).

## Kafka producer в сервисе

Из messaging-артефакта (`openapi-codegen` 1.7.0+, ADR-26061101) генерируется `{Schema}V{Major}MessageBuilder`.

1. Сформируйте `MessagePayload` в сервисе.
2. Вызовите `withPayload(payload)` или `withPayload(payload, key)` — обязательные заголовки (`schemaName`, `schemaVersion`, `createdAt`, `uuid`) выставляются автоматически.
3. При необходимости добавьте прикладные заголовки через `.setHeader(...)` на возвращённом Spring `MessageBuilder`.
4. Опубликуйте через `StreamBridge.send(binding, message.build())`.
